# Flutter mobile app — production plan and roadmap (senior mobile review, v2)

## Context
Backend (Django + DRF, ~900 green tests) covers every module: auth, products, customers, suppliers, milk collection, supplier payments, routes / standing orders / route runs, deliveries, billing, shop sales, stock / production, expenses / salary, reports. ROADMAP Phase 11 (frontend) is not started; Phase 12 (deployment) is partial. Goal: one Flutter codebase shipping production-grade Android + iOS apps for OWNER / MANAGER / STAFF, offline-capable for field and counter entry, in Hindi + English, on cheap Android phones used in rural India.

Status: draft for owner review. No code until approved.

## 0. What the senior review changed (v1 → v2)

| # | Gap found in v1 | Fix in v2 |
|---|-----------------|-----------|
| R1 | No design phase; screens would be invented while coding | **M1 UX & design** (wireframes → Figma → Hindi labels approved by client) before any feature screen |
| R2 | Phone clock can be wrong (cheap phones, manual time); backend rejects future timestamps → offline entries fail | Server-time offset from the HTTP `Date` header; timestamps = device time + offset; warn user when skew > 5 min |
| R3 | Staff can be offline longer than the refresh token (7 days) or a different user logs in on the same phone → outbox sent as the wrong person | Outbox rows bound to `user_id + business_id`; only that user's session may send them; re-login of another user is blocked until the queue is synced or explicitly exported/discarded by OWNER |
| R4 | Crash between "tap save" and "write outbox" loses or duplicates an entry | `client_ref` generated on tap and written to Drift in **one transaction** with the local row before any network call; save button disabled while the transaction runs |
| R5 | Offline entries that depend on each other (quick customer created offline, then a sale for it) | v1 rule: **master data (customers, suppliers, products) is online-only**; offline writes only reference already-synced ids |
| R6 | Chinese OEM Android phones (Xiaomi, Oppo, Vivo, Realme) kill background jobs | Do not depend on `workmanager`; sync on app open / resume / connectivity change / after each save + a visible **"Sync now"** button and "last synced" time. Background job is best-effort only |
| R7 | Local DB holds customer names, phones, balances unencrypted | Drift on **SQLCipher**; key generated per install, kept in secure storage. Android `allowBackup=false` so tokens / DB are never restored onto another phone |
| R8 | Logout left PII cached | Logout wipes read cache; only unsynced outbox survives (encrypted) |
| R9 | No remote control after release | `app-config` endpoint also carries **maintenance mode**, **min version (force update)**, **feature flags** |
| R10 | Release builds readable, crashes unreadable | `--obfuscate --split-debug-info`, symbols uploaded to Sentry; staged rollout 10% → 50% → 100% |
| R11 | App would be empty at pilot | **Data import** (customers, suppliers, rates, opening balances from paper) is a pilot prerequisite (ROADMAP Phase 12 item) |
| R12 | Full re-download of lists on every refresh on 2G/3G | v1 is fine (hundreds of rows, page_size 200); add `updated_after` filter on master lists **only if** pilot data shows slow refresh (B7, measured, not speculative) |
| R13 | No device matrix, no support tooling | Test matrix of real low-end devices; in-app **"Send diagnostics"** (last 500 log lines, no tokens / PII) |
| R14 | Estimates had no buffer, no store-review time | +20% buffer, App Store review and Play closed-testing time included |
| R15 | No definition of done, risks, or success metrics | Added sections 11, 12, 13 |
| R16 | Generated API client committed into app code | Generated client lives in `packages/dairy_api` (pinned generator version, regenerated by one script, never hand-edited); app wraps it in repositories |
| R17 | Flutter version drift between machines / CI | Pin Flutter with **FVM** (`.fvmrc`), same version in CI |

## 3. App architecture

```
dairy_mobile/
  .fvmrc
  packages/dairy_api/        generated client (never hand-edited)
  lib/
    main_dev.dart, main_staging.dart, main_prod.dart
    app/       router, theme, flavors, l10n, app-config gate
    core/
      api/     dio, interceptors, error mapping, server-clock offset
      auth/    token store, session controller, single-flight refresh
      db/      drift + sqlcipher, tables, migrations
      sync/    outbox, sync engine, failure list
      money/   Decimal parse / format
      time/    business-timezone day ranges (half-open), shift display
      logging/ ring-buffer logger, diagnostics export
      widgets/ amount field, qty field, searchable picker, states
    features/<feature>/{data,domain,presentation}
      auth, business_select, dashboard, customers, suppliers, products,
      routes, route_runs, deliveries, milk_collection, supplier_payments,
      billing, customer_payments, sales, stock, production, expenses,
      salary, reports, settings, sync_center
```

Rules:
- Screens → controllers → repositories → `dairy_api`; screens never touch Dio.
- **Error mapping:** DRF 400 field errors under the matching form field; 401 → one refresh then logout; 403 → "no permission"; 429 → "try again in N s" (from `Retry-After`); 5xx / network → retry or queue.
- **Business context provider** (`business_id`, role, timezone, bill_language from `/me/`); switching business clears caches.
- **Role guards** in the router mirror backend (STAFF / MANAGER / OWNER; salary OWNER only). Backend stays the real guard.
- **Time:** "today" and day filters computed in `Business.timezone`, never phone zone; timestamps ISO 8601 with offset, corrected by server-clock offset (R2), never future.
- Requests send only documented fields (backend rejects unknown fields with 400).

## 4. Auth & session
- Login `auth/token/` → store tokens → `auth/me/` → 1 business: enter; many: picker; none: "ask owner to add you".
- Access 30 min, refresh 7 days, rotation on. **Single-flight refresh** with a mutex: the backend kills every session when a rotated refresh token is reused after 10 s, so parallel refreshes must never happen. Persist the new refresh token before using the new access token.
- Revoked session (logout elsewhere, password change, theft detection) → clear tokens, keep the encrypted outbox, login screen with "session ended" message.
- Logout with unsynced outbox: blocked with "N entries not synced — Sync now" (R3).
- Forgot / reset (OTP email), change password, app lock on resume.

## 5. Offline-first design

**Offline writes (v1):** route-run entries, ad-hoc delivery, delivery cancel, milk collection create, shop sale create (existing customers only, R5).
**Online-only:** master data, bills (generate / finalize / void), payments, reversals, allocations, corrections, salary, rates, prices, stock, reports.

Outbox row: `id, user_id, business_id, client_ref (UUIDv4), method, path, body_json, created_at, status (pending|sending|done|failed), attempts, last_error, server_id, server_number`.

Sync engine:
1. Row written in the same Drift transaction as the local optimistic row (R4).
2. FIFO per business, one request at a time; a `sending` row found at startup is resent with the same `client_ref` (server replays).
3. Network / 5xx → exponential backoff with jitter, capped; same `client_ref`.
4. 400 (frozen bill period, run closed, missing rate, same ref + different data, deactivated product) → `failed`, shown in **Sync center** with the server message; user fixes and resends (new `client_ref`) or OWNER/MANAGER discards with reason (kept in local log).
5. 401 → pause until the same user logs in again; 403 → `failed`.
6. Server-generated numbers (can label, sale / bill numbers) show "pending" until synced, then stored.
7. Triggers: after each save, app open / resume, connectivity regained, "Sync now", best-effort background (R6).

Read cache (encrypted): products + current sale prices, customers, suppliers, routes, today's run + tasks, standing orders. Refreshed on login, pull-to-refresh, after sync. Offline prices labelled "may be outdated"; the server always applies its own price / rate (snapshot rule).

## 6. Screens by role (mapped to existing endpoints)

**All:** login, forgot / reset / change password, business picker, language (en / hi), settings, Sync center, send diagnostics, about / version.

**STAFF — delivery (phone, field, offline)**
- Today's route run: `GET/POST route-runs/`, tasks `route-runs/<id>/tasks/`.
- Task list prefilled from standing orders → one tap Delivered / change qty / Skipped → `route-runs/<id>/entries/` (offline).
- Extra delivery `deliveries/`; cancel with reason `deliveries/<id>/cancel/`.
- Close run `route-runs/<id>/close/` (online; refuses while outbox has items).
- Only assigned routes (backend enforces `assigned_to`).

**STAFF / MANAGER — counter / collection centre (phone or tablet)**
- Milk collection, one row per can: supplier by code → milk type → litres → fat (BUFFALO only; COW sends no `fat` key) → shift auto from time, editable → `suppliers/<id>/milk-collections/`. Today list, daily summary `milk-collections/daily-summary/`, cancel / correct (manager, online).
- Shop sale: product grid → qty → customer (walk-in / existing) → payment method → `sales/`; summary `sales/summary/`; cancel / correct (manager, online).

**OWNER / MANAGER**
- Dashboard `reports/dashboard/daily/`.
- Customers: list / search / create / edit, balance, statement, opening balance, standing orders, route customers, quick customer.
- Billing: list + filters, generate `bills/generate/`, per-customer bill, detail, finalize, void (reason), PDF view + WhatsApp share (`?lang=hi|en`).
- Customer payments: record (CASH / UPI / BANK_TRANSFER / CHEQUE / OTHER), allocate, reverse (reason).
- Suppliers: CRUD, milk rates (effective-dated, correct), balance, statement + print, pay summary, payments / allocate / reverse.
- Purchases (non-milk): create, receive, cancel, returns, corrections, adjustments.
- Products: categories, products, prices `products/<id>/prices/` (never backdated).
- Routes: CRUD, customer order, standing orders, reopen run.
- Stock: balances, adjustments / wastage, production batches (create / cancel / correct).
- Expenses: categories (owner), create / cancel / correct, summary.
- Reports: milk balance, closing stock, profit ("operational estimate"), supplier balances / ledger, customer outstanding, stock, product sales, expenses; `?export=csv|pdf` + share; date pickers enforce 92 / 366-day limits.

**OWNER only:** salary (employees, generate month, accruals, bonus / deduction, payments, balances, statements). Managers see salary as "hidden".

## 7. UX & quality bar
- Designed first (M1): wireframes for the 6 core flows, tested with real staff on paper before Figma.
- Hindi + English; staff default Hindi. Western digits (0–9) everywhere for numbers.
- Big touch targets (≥ 48 dp), numeric keypads, minimal typing, search by code, last-used supplier / product remembered.
- Destructive actions ask for a reason and confirm; double-tap protection on every submit.
- Loading / empty / error / offline states on every screen; pull-to-refresh; infinite scroll.
- Text scale up to 1.3x without overflow; screen-reader labels; high-contrast outdoor theme.
- Layouts: 360 dp phones and 8–10" tablets (two-pane at counter).
- Performance budget: cold start < 3 s and 60 fps lists on a 3 GB RAM Android 9 phone; release AAB download < 25 MB.

---

## 8. Security
- Tokens and DB key only in secure storage; Drift encrypted (R7); `allowBackup=false`.
- No tokens / PII in logs or Sentry (scrubbing hook); diagnostics export redacted.
- Obfuscated release builds; no secrets in the app (base URL only).
- HTTPS only; Android `network_security_config` blocks cleartext in prod. Certificate pinning: not in v1 (pin rotation risk outweighs the benefit for this threat model); revisit if required.
- Root / jailbreak detection: not in v1.

## 9. Testing strategy
- **Unit:** Decimal parse / format, timezone day ranges, clock-offset correction, outbox state machine, single-flight refresh, error mapping.
- **Repository:** mocked Dio with real API response fixtures (including 400 shapes).
- **Widget + golden:** core screens in en / hi, phone and tablet.
- **Integration (staging backend, seeded):** login → run → 20 deliveries offline → kill app → reconnect → server has exactly 20 rows, one per `client_ref`.
- **Chaos:** airplane toggles mid-send, kill during sync, token expiry during sync, wrong phone clock, two devices same user, other user logs in with a pending queue.
- **Maestro** smoke flows on real devices before every release.
- **Device matrix:** Redmi / Realme / Samsung M-series (Android 9–15, 3–4 GB RAM), one 8" Android tablet, iPhone SE + a current iPhone.
- Coverage: `core/` ≥ 85%, features ≥ 60%.

## 10. Release & operations
- Flavors with separate app ids; prod `com.<company>.dairy`.
- Android: signed AAB, Play App Signing, internal → closed testing (client staff) → production with staged rollout. Min SDK 24; target SDK = Play's required level at release time.
- iOS: TestFlight → App Store (privacy policy URL, reviewer demo account on a demo business). Min iOS 13.
- Versioning: semver + CI build number; force update via `app-config`.
- Store listing in Hindi + English, screenshots, Play data-safety and Apple privacy labels.
- Monitoring: Sentry release health (crash-free sessions), backend uptime, backup restore drill monthly.
- Runbook (Readme.md): release steps, rollback (halt staged rollout, raise min version only after a fix ships), key rotation, support flow using diagnostics.

## 12. Risks

| Risk | Mitigation |
|------|------------|
| OEM battery killers stop background sync | Foreground-triggered sync + "Sync now" + last-synced indicator (R6) |
| Wrong phone clock | Server-time offset + skew warning (R2) |
| Staff resist the app / paper habit | Paper test in M1, Hindi-first UI, parallel paper run in Pilot 1 |
| API contract change breaks old builds | Generated client from schema in CI, `/api/v1/` frozen, force update via app-config |
| No Mac for iOS | Codemagic cloud builds |
| Token theft rule logs users out unexpectedly | Single-flight refresh, persisted before use, tested |
| Data import errors make balances wrong | Import dry-run report + owner sign-off before pilot |

## 13. Success metrics (pilot and launch)
- Crash-free sessions ≥ 99.5%.
- 0 duplicate rows from sync (checked by `client_ref` count).
- A delivery entry ≤ 3 taps; a milk collection can ≤ 10 s.
- Month-end billing done in the app in < 1 hour (was 3–4 days).
- Sync backlog cleared within 1 min of regaining network.
