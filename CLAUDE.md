## Production-grade planning checklist (do this BEFORE presenting any plan)
Past plans needed several revisions because these were found late. Inspect the real code first (models, constraints, services, selectors, migrations, tests), then answer each item in the plan itself:
1. **Reuse existing policy**: find how the codebase already decides the same question (e.g. stock shortfall is recorded and flagged, never blocked; statements already filter `status=RECEIVED`). Do not invent a second rule.
2. **Concurrency**: name every writer of the same rows and the global lock order (purchase -> payment; route run -> delivery -> product). New writers must follow it; add a real threaded/transaction test, not only a sequential one. Postgres FOR UPDATE on a parent row also blocks FK inserts into it: use `no_key=True` for parent rows. Check a design premise ("X must be blocked") against how balances/selectors already treat the case before building it.
3. **Idempotency**: `client_ref` replay compares the full normalized request (including defaulted fields like shift and time); same ref + different data is an error.
4. **Uniqueness**: every generated or supplied identifier has a DB constraint, not only an app check.
5. **Time**: use `Business.timezone`; day ranges are half-open `[start, next_day_start)`; corrections keep the original timestamp and re-resolve the rate at that time.
6. **Inventory**: say what happens to stock when the reversed quantity was already consumed (negative balance is flagged, not hidden). Product mapping validates same business, milk type and unit.
7. **API contract**: say exactly which fields are rejected, ignored or required per case; no "reject/ignore" ambiguity.
8. **Migrations**: backfill without recomputing money; test on a copy of the dev DB; reversible.
9. **Visibility**: if something silently does not happen (e.g. no stock mapping), expose it in the API response.
10. **Audit**: cancel/correct keep reason, who, when; admin is read-only for ledger rows, no delete.
11. **Regression**: run affected app tests after each step and the full suite at the end.
Also: when the owner pastes an external review, verify every claim against the code and say which are already handled, which are valid, and which are wrong.

## Architecture rules
- Money and stock are append-only ledgers: never edit or delete; correct with cancel/reversal/adjustment rows that keep an audit trail (reason, who, when).
- Snapshot prices and rates on the row; later rate changes never recompute old records.
- Logic lives in the service layer (apps/<app>/services.py); views stay thin. Use transaction.atomic and select_for_update on contested rows; DB constraints are the final guard.
- Retry-safe creates use client_ref (unique per business).
- Tenant scoping on every queryset; roles OWNER/MANAGER/STAFF via IsBusinessMember. Purchases and cost data are OWNER/MANAGER only.
- Lists use StandardPagination. Errors go through raise_api_validation_error.
- Tests live in tests/<area>/; the full suite (about 900 tests) must stay green.

## Business decisions already made
- Milk purchase: BUFFALO = litres x fat x rate; COW = litres x flat rate (no fat stored; fat-based cow is a future feature). Rate is per supplier + milk type, effective-dated.
- COW requests that include a `fat` key (even 0) are rejected with 400; BUFFALO requires fat > 0.
- One MilkCollection row per can, with shift (MORNING/EVENING). The user may pick the shift; if omitted it is derived from the request's `collected_at` in the business timezone (before 15:00 = morning).
- Can label / collection_number is server-generated only (client cannot send it): `<SUPPLIER_CODE>-<YYMMDD>-<M|E>-<C|B><seq>`, e.g. RAM01-261015-M-B2. Never reused, even after cancel.
- Milk entries are never deleted: cancel with reason, or Correct (cancel + replacement at the original time/shift). Cancel/Correct is ALLOWED even if a payment is allocated: balances and the allocator ignore allocations on CANCELLED purchases, so the money returns to the supplier's available credit (the earlier "blocked" idea was wrong - verified in apps/payments/selectors.py).
- If cancelling consumed milk makes stock negative: allow and flag the shortfall (same as deliveries), never block.
- Lock order for milk: business (select_for_update(no_key=True)) -> purchase -> collection -> product. Never use a plain FOR UPDATE on the Business row: it blocks every INSERT that references the business and deadlocks against purchase/payment locks (found by the cancel-vs-correct race test).
- Milk bought posts to stock via a per-business Cow/Buffalo product mapping.
- Purchase corrections use Option D (returns and corrections through the immutable PurchaseAdjustment ledger).
- Deliveries can never be deleted; stock timestamp policy is ARCHITECTURE.md section 13.
- Payments: reversals may be partial and are posted only via `reverse_supplier_payment` (advance first, then allocations newest-first through `SupplierPaymentAllocationReversal` rows). `get_supplier_position` is the single place supplier money is summed; outstanding is never clamped. Run data migrations separately from schema migrations (Postgres pending-trigger-events error).
- Customer money (Phase 5): the receivable is a FINALIZED `CustomerBill`; deliveries are only its source. Unbilled deliveries are reported separately and never counted in the balance. Sign: positive = customer owes, negative = advance. Customer payments, allocations, reversals and unwind rows mirror the supplier design; allocations on VOID bills are ignored (the money returns to credit); one `get_customer_position` sums customer money.
- Every bill carries an explicit period (`period_start`/`period_end`: inclusive local dates in `Business.timezone`, queried half-open on `delivered_at`, never on `delivery_date`). Nothing is stored on Customer. Finalize only after the period has ended.
- A FINALIZED bill freezes that customer's period: creating, cancelling or correcting a delivery dated inside it is refused until the bill is voided (reason required); a void spawns a replacement DRAFT. Bills are never edited.
- Lock order now: route run -> customer (`select_for_update(no_key=True)`) -> bill -> delivery -> payment -> product. Every writer of a customer's deliveries, bills or payments takes the customer lock first.
- Bill and payment numbers are server-generated only (clients cannot send them) and never reused: bill `<CUSTOMER_CODE>-<YYMMDD of period start>-<seq>`, payment `PAY-<CUSTOMER_CODE>-<YYMMDD>-<seq>`.
- Opening balances: an owed amount is a FINALIZED OPENING bill (one live per customer); a prepaid amount is an advance payment (method OTHER).
- Billing API: OWNER/MANAGER only; unknown request fields are rejected with 400; money values are JSON strings; the bill PDF uses reportlab, English ("Rs.") or Hindi ("₹") via `?lang=en|hi`, default `Business.bill_language` (set in admin); Devanagari is shaped by the Phase 9 Pillow/Raqm renderer.
- Stock (Phase 7): wastage / adjustments and production batches are OWNER/MANAGER only; the stock balance API (quantities) is readable by any member; the milk balance and closing stock reports are OWNER/MANAGER only. Shortfall on adjustments, wastage and production inputs is flagged on the row, never blocked. Adjustment (`ADJ-`) and batch (`PRD-`) numbers are server-generated and never reused. Production is free-form (no recipes, no unit conversion); yield is display only. Closing stock is live, valued at the owner-set PURCHASE `ProductPrice`; missing cost = `unvalued`, never zero. Lock order for adjustments and production: business (`no_key`) -> adjustment / batch -> products sorted by id.
- Input and access rules (audit pass): bad client input must be a 400, never a 500 (use `milk_queries._date_param` for query dates; wrap `parse_datetime`, which raises on impossible values). A NUL character is rejected by `RejectNullBytesMiddleware`. Supplier milk rates and PURCHASE (cost) prices are OWNER/MANAGER only, reads included. Prices are set through `POST products/<pk>/prices/`, never backdated. `NUM_PROXIES` must stay an integer (0 = no proxy); never map it to `None`. Never take a plain `FOR UPDATE` on a Business row (use `no_key=True`). Ledger models block queryset `update`/`delete`; ledger admins are read-only.

- Expenses and salary (Phase 8): expenses are OWNER/MANAGER; all salary data (employees, accruals, payments, balances) is OWNER only, reads included, and must stay owner-only in Phase 9 dashboards. Categories are owner-created. `expense_date` is a local date (past allowed, never future, no month freeze). Salary has no allocations: balance = salary + bonus - deductions - payments, positive = owed to the employee, negative = advance; an overpayment is never blocked. The owner presses "generate month" (no scheduler); salary is pro-rata by calendar days for joiners / leavers and snapshots days and amount on the row. Bonus / deduction are typed entries with a reason. Salary cost counts in the month it belongs to, not when paid. Employees are not linked to app logins; an expense `payee` is free text. Lock order: business (`no_key`) -> employee (`no_key`) -> accrual / payment.
- Reports (Phase 9): `apps/reports`. All OWNER/MANAGER only; salary figures are OWNER only (hidden from managers, flagged in the response). Sales are counted on delivery / sale date (accrual); purchases = milk collections + non-milk RECEIVED purchases + adjustments (never also the mirror purchase of a milk collection). Collections: CASH = cash; UPI, BANK_TRANSFER, CHEQUE = online; OTHER separate. Profit is an "operational estimate", never called accounting profit. Bulk customer / supplier balances (`reports/positions.py`) must always equal `get_customer_position` / `get_supplier_position` (tested). One table dict feeds JSON, CSV and PDF; export param is `export=csv|pdf` (`format` is reserved by DRF). CSV: UTF-8 BOM, text cells guarded against formula injection. PDF: Hindi is drawn by Pillow/Raqm (reportlab cannot shape Devanagari), bundled Noto Sans Devanagari (OFL). Limits: list reports 92 days, profit and supplier ledger 366, PDF 5,000 rows. Exports are throttled (`reports_export`).
- Auth (QA pass): access tokens carry `sid` (login session) and `pwd` (password stamp); logout, password change/reset and refresh-token theft all revoke them via `apps/users/authentication.py`. A rotated refresh token reused after 10 s ends the user's sessions. Auth emails (OTP, "password changed") go from a background thread (`EMAIL_ASYNC`, inline in tests). Production (`DEBUG=False`) requires `REDIS_URL`; `NUM_PROXIES` is 0 unless a real proxy sits in front. Run `flushexpiredtokens` and `purge_password_otps` daily.
- Mobile app (Phase 11): Flutter, one codebase; **Android first to GA, then iOS**. Designed for nationwide scale (1M+ shops). The plan and roadmap live in MOBILE_APP_PLAN.md; keep it updated. Shop owners sign up themselves; phone OTP is the main login and sign-up happens only after OTP verification (password login stays as fallback). OTP login and self sign-up come in M11, before public launch; until then password login and shops created by import / admin. Phone numbers are stored as +91 E.164 from now. The app is free at launch; pricing comes later, so add no billing code now, only keep limits in one place.
- Documentation: after a feature, fix or decision that affects setup, security or operations, record it in Readme.md (owner request).
- QA sweeps (all modules, see QA_LOG.md): follow the API rules in Readme.md section "QA log and API rules" (unknown fields 400, sane dates 2000-2100, offset-aware timestamps, never future, money as strings, paginated stable lists, duplicates 400, frozen codes, soft delete with guard). Keep QA_LOG.md updated when a bug is found; open questions go to its OPEN rows.
- Staff management (23 Oct 2026): OWNER manages MANAGER/STAFF, MANAGER manages STAFF, through `businesses/<id>/staff/`; OWNER rows and self are never edited via API. Staff logins are created without a password and start with an owner-issued one-time code (reuses `PasswordResetOTP`). A reset code is refused for people who also work in another active shop, Django staff/superusers and inactive members. Phones are `+91` E.164 and unique when set; usernames are unique ignoring case; reset identifier may be username, email or phone. `GET auth/me/` lists own active memberships.
- Shop delete / restore (23 Oct 2026): only the shop's OWNER deletes (`DELETE businesses/<id>/` with `confirm_name`) and restores (`POST businesses/<id>/restore/`); soft delete only, no balance guard, no time limit. A deleted shop is unreachable for everyone; `auth/me/` returns `deleted_shops` for owners. Staff reactivation rules are unchanged (owner for managers, owner or manager for staff).
